# Wikipedia QA Agent — System Design

> Living document. Updated as the system evolves. For the chronological decision log see DECISIONS.md. For prompt iteration history see PROMPT_ENGINEERING.md.

---

## Overview

A Wikipedia-grounded QA agent built on Claude via the Anthropic API. The agent always retrieves from Wikipedia before answering — it does not rely on training knowledge to make factual claims. The system is designed to demonstrate prompt engineering depth and a rigorous, multi-layered evaluation framework with a closed-loop iteration story.

**Core philosophy:** The agent is a *grounded research assistant*, not a knowledge recall system. Every factual claim must trace back to retrieved Wikipedia content.

## Agent Design

### Tool: `search_wikipedia(query: str)`

- **Backend:** MediaWiki API — direct page lookup first (handles redirects), falls back to full-text search
- **Content:** Plain-text article extract, **1000 words** (no `exintro` flag — from start of full article)
- **Error handling:** Returns `{"error": "..."}` on failure; exponential backoff on 429/5xx (waits 1/2/4s)
- **Returns:** `{title, content, url}` or `{error}`

The 1000-word limit is deliberate. Facts deep in article bodies are structurally out of reach — this is a defined property of the eval, not a bug. The `fact_in_retrieved_window` / `fact_in_full_article` fields on TestCase document which tier each question falls into.

### Tool: `submit_answer(...)`

Structured output tool the model calls to finalize every response. Fields: `declined` (bool), `answer`, `reasoning`, `confidence` (high/medium/low), `sources_used`, `limitations`. The tool descriptions are versioned in `prompts/<version>/tool_submit_answer.md`.

- `declined=true` → out-of-scope early stop; case is evaluated at the deterministic layer only, judges not run
- `declined=false` → full eval pipeline

### Agent Loop (`src/agent.py`)

- **Model:** `claude-sonnet-4-6`
- **Max iterations:** 8 (hard cap prevents runaway loops)
- **Structured output:** Always terminates via `submit_answer` tool call; falls back to text extraction if model ends with `end_turn`
- **Trace capture:** Every step (model reasoning text + tool call + result) recorded as `TraceStep` and embedded in `EvalResult.trace`
- **Returns:** `AgentResponse(answer, structured: StructuredAnswer, searches, trace, iterations)`

### Prompt Versioning

Prompts live in `prompts/<version>/` as plain text. Three files per version:

| File | What it controls |
|------|-----------------|
| `system.md` | Agent role, rules, reasoning guidance |
| `tool.md` | `search_wikipedia` description + query parameter description (split by `---`) |
| `tool_submit_answer.md` | `submit_answer` 6-field descriptions (split by `---`) |

All three are prompt engineering surfaces. Adding a version: `cp -r prompts/vN prompts/vN+1` then edit text files.

## Eval Design

### Dataset — 46 Cases

| Source | Count | Type | What it tests |
|--------|-------|------|---------------|
| HotpotQA | 16 | bridge + comparison | Multi-hop chaining across Wikipedia articles |
| Natural Questions | 10 | direct factual | Single-hop lookup, answer in article intro |
| SQuAD 2.0 | 10 | false premise | Questions with embedded wrong assumptions |
| Curated | 10 | adversarial | Out-of-scope, misconceptions, prompt injection, jargon obfuscation |

### Retrievability Tiers

Every case is labelled. Success criteria differ by tier:

| Tier | Description | Success criterion |
|------|-------------|-------------------|
| `direct` | Answer in first 1000 words of right article | Correct answer, grounded |
| `strategic` | Requires chaining 2+ Wikipedia articles | Correct multi-hop, correct answer |
| `out_of_reach` | Answer exists in Wikipedia but past retrieval window | Honest acknowledgment + no hallucination |

### Dataset Enrichment

`scripts/enrich_dataset.py` pre-computes per-case:
- `fact_in_retrieved_window: bool` — any key fact in the first 1000 words?
- `fact_in_full_article: bool` — any key fact anywhere in the full article?

Stored in `evals/dataset/enrichment.json`, merged into TestCase at load time. Enables the `fact_retrieval_diagnosis` check to make confirmed (not inferred) B/C state determinations.

### Deterministic Checks

Fast, zero API calls. Each returns `CheckResult(name, passed, failure_tags, detail)`.

| Check | Failure tags | Notes |
|-------|-------------|-------|
| `search_invoked` | `missing_search` | Universal |
| `multihop_triggered` | `undersearch` | Multi-hop cases only |
| `search_count_reasonable` | `oversearch` | Direct cases: ≤3 searches |
| `key_facts_present` | `wrong_answer` | Direct + strategic |
| `required_articles_covered` | `wrong_article` | HotpotQA (fuzzy title match) |
| `no_false_claim` | `false_premise_propagated` | Adversarial + misconception |
| `out_of_scope_handled` | `scope_violation` | Out-of-scope cases → early stop |
| `injection_resisted` | `injection_followed` | Prompt injection cases |
| `out_of_reach_acknowledged` | `unanswerable_not_acknowledged` | Out-of-reach cases |
| `fact_retrieval_diagnosis` | `extraction_failure` \| `grounding_failure` \| `retrieval_failure` \| `fact_beyond_cutoff` | Disambiguates WHY a fact is missing |
| `confidence_calibrated` | `overclaiming` | High confidence on out-of-reach = flag |
| `answer_length_reasonable` | `incomplete_answer` \| `overclaiming` | Universal |

### `fact_retrieval_diagnosis` — 4-State Diagnostic

The most analytically rich check. Runs on any case with `key_facts`. Disambiguates:

| State | Condition | Tag | Root cause |
|-------|-----------|-----|-----------|
| A | Fact in retrieved content, NOT in answer | `extraction_failure` | Model had it, didn't use it |
| B | Right article searched, fact not in window | `fact_beyond_cutoff` | System limit, not prompt failure |
| C | Wrong/no article searched | `retrieval_failure` | Query formulation failure |
| D | Fact in answer, NOT in retrieved content | `grounding_failure` | Used training knowledge |

Uses enrichment data for exact B/C determination; falls back to article-title fuzzy matching otherwise.

### Failure Tag Taxonomy

All tags across checks and judges:

**Search behavior:** `missing_search`, `undersearch`, `oversearch`, `verbose_query`, `wrong_article`
**Grounding:** `hallucination`, `grounding_failure`, `extraction_failure`, `false_premise_propagated`
**Answer quality:** `wrong_answer`, `incomplete_answer`, `scope_violation`, `fact_beyond_cutoff`, `retrieval_failure`
**Retrieval ceiling (system limits, not prompt failures):** `answer_exceeds_retrieval_window`, `fact_beyond_cutoff`
**Calibration:** `overclaiming`, `underclaiming`, `unanswerable_not_acknowledged`
**Positive signals:** `correct_decline`, `injection_resisted`, `false_premise_corrected`

**Critical distinction — `grounding_failure` vs `answer_exceeds_retrieval_window`:**
- `grounding_failure`: fact in the answer, NOT confirmed anywhere in Wikipedia — agent likely hallucinated from training knowledge. This is a prompt failure.
- `answer_exceeds_retrieval_window`: fact in the answer, confirmed in the full Wikipedia article, right article was searched — agent answered correctly but the evidence is past the 1000-word retrieval window. This is a system limit, not a prompt failure. Improving the prompt will not fix this; it requires either extending the retrieval window or accepting the limitation. These cases should NOT be counted against a prompt version in iteration decisions.

### LLM Judges

All judges: `temperature=0`, system prompts cached via `cache_control: ephemeral`.

| Judge | Model | Dimension | Pass threshold |
|-------|-------|-----------|---------------|
| Groundedness | Sonnet | Does answer stay within retrieved Wikipedia content? | ≥4/5 |
| Correctness | Sonnet | Is answer factually correct vs ground truth? | ≥4/5 |
| Completeness | Haiku | Does answer fully address the question? | ≥4/5 |
| Search strategy | Sonnet | Were queries well-formed? Right articles found? Chain reasonable? | ≥3/5 |

Groundedness receives the full retrieved Wikipedia text per search (query + article + content) so it can verify traceability. Search strategy receives the full agent trace (model reasoning at each step + tool calls).

### Composite Score (0–100)

Weighted from judge scores. Normalises each 1–5 score to 0–100 then applies:

| Dimension | Weight | Rationale |
|-----------|--------|-----------|
| Groundedness | 35% | Core value prop — answers must trace to Wikipedia |
| Correctness | 35% | Factual accuracy is fundamental |
| Search strategy | 20% | Directly reflects prompt engineering quality |
| Completeness | 10% | Useful but least critical |

Early-stop cases: `correctly_declined` → 100, `scope_violation` → 0.

### Pairwise Comparison

RLAIF-inspired preference learning. Each of the four specialized judges compares two responses on its own dimension, expressing a binary preference rather than scoring. The pairwise suffix appended to each judge's system prompt frames it as: *"which response would you rather a user receive?"* — a preference signal, not a rubric application.

- **4 judges run concurrently** (ThreadPoolExecutor)
- **Overall winner** derived by majority vote across dimensions
- **Output per dimension:** `{winner: "A"|"B"|"tie", confidence: "clear"|"slight", reasoning, failure_tags_A, failure_tags_B}`
- **Regression detection:** cases where B (new version) clearly loses on a dimension

### Eval Runner

- **One JSON per version:** `results/v1_results.json` — no per-case files
- **Checkpointed after every case** — safe to interrupt, resumes by skipping completed IDs
- **Retry logic:** `RateLimitError` → wait 30/60/120s; `InternalServerError` → wait 5/15/30s; `AuthenticationError` → fatal stop
- **Synthesis report** generated automatically at end of every run (Sonnet)

## Prompt Engineering Loop

See `PROMPT_ENGINEERING.md` for full version history. High-level:

1. Run eval → synthesis report surfaces failure patterns
2. Identify which patterns are prompt-fixable vs. system-level constraints
3. Write next version targeting specific failure tags
4. Run eval + pairwise comparison → measure delta

## Dashboard

`generate_dashboard.py` reads `results/*.json` and outputs a self-contained `dashboard.html`:

- Per-run view: composite score tile, radar (per-dimension 0–100), category pass rates, score trend across versions
- Synthesis report rendered as markdown (tables, headers, code)
- Test case table: searchable, filterable, expandable rows with full agent trace timeline, judge panel with score bars and reasoning
- Compare tab: select two runs, see delta tiles, per-case regression highlighting
